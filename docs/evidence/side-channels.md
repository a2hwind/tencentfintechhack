# Side-channel checks

_Generated by `scripts/leak_eval.py` · planner: heuristic · answerer: extractive-stub · embeddings: hash-256_

A denied query must be indistinguishable from an empty one. Three channels are checked: the response body, its shape, and its timing.

## Body and shape

`ctr-lee` asks for the restricted Q3 breach report and for a report that does not exist. Response bodies byte-identical: **True**. Both carry no citations, no provenance and the same message; the audit sequence number travels in a response header, never in the body.

## Timing

40 interleaved runs per arm, same user, same process, measured at the HTTP client:

| Arm | median ms | p95 ms | mean ms | stdev ms |
|---|---|---|---|---|
| denied (restricted document matches) | 28.6 | 29.9 | 29.1 | 2.6 |
| no match (nothing matches) | 29.0 | 30.8 | 29.3 | 1.8 |
| answered (jdoe, for scale) | 19.0 | 29.7 | 21.4 | 7.8 |

Median difference denied − no match: **-0.3 ms** (spread within each arm: ±2.6 ms). Gate 1 runs inside the index query whether or not anything is permitted, Gate 2 only runs on already-permitted candidates, and every empty result is held to a constant-time floor (`NO_RESULT_MIN_LATENCY_MS`, 25.0 ms) so that writing a denial to the audit log costs no observable time.

## Other channels, by construction

- No counts: the API never reports how many candidates were filtered (`internal_brain/core/pipeline.py`).
- No hints from expansion: a linked item that fails Gate 1 or Gate 2 is dropped silently (`core/retrieve.py`, `core/verify_live.py`).
- No hints from errors: an adapter failure is `unverifiable` and produces the same uniform message (`core/verify_live.py`).
- No hints from suggestions: the UI's example questions are static; there is no autocomplete over titles.
- The real reason (`deny:not_member`, `deny:revoked`, `no_match`) goes only to the audit log, readable by the compliance role and logged when read.
